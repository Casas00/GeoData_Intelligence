# Dataset schema versioning

## 1. Purpose

This document defines how GeoData Intelligence identifies, versions and evolves logical dataset schemas, and how datasets should move from one schema version to another.

A logical schema describes the structure expected for a dataset: its attributes, their data types and, where applicable, its geometry type and Coordinate Reference System (CRS).

The logical schema is distinct from the physical PostgreSQL table that stores the dataset's records.

## 2. Schema identity and version

Each logical schema record is stored in `metadata.dataset_schemas` and has the following relevant properties:

| Property | Purpose |
|---|---|
| `schema_id` | Internal primary key generated by the database. |
| `schema_code` | Unique code generated by the application. |
| `name` | Name identifying the logical schema family. |
| `version` | Integer identifying a version within that family. |
| `definition` | JSONB document describing the logical structure of that version. |
| `description` | Descriptive metadata; it is not part of the structural definition. |
| `created_at` | Timestamp of record creation. |

The database enforces uniqueness for `schema_code` and for the combination of `name` and `version`.

### 2.1. `schema_id`

`schema_id` is the stable primary key of one specific schema-version record. It is generated by PostgreSQL and must not be manually assigned or changed.

A new version is a new record and therefore receives a new `schema_id`.

### 2.2. `schema_code`

`schema_code` is a unique, application-generated identifier for one schema version. It is generated from the schema name and version, with alternative prefixes used if a collision occurs.

The code is assigned by the service, not by the AI component or API client. Once created, it must remain unchanged.

The code generator uses a version component formatted with three digits (for example, version 1 becomes `001`). The prefix is derived from the schema name; collision handling can select an alternative prefix.

Examples of the general format:

```text
HYDRO001
ROADS001
```

These are illustrative examples of the format, not reserved codes.

### 2.3. `name` and `version`

`name` identifies the logical schema family. `version` identifies a particular structural revision of that family.

For a given name, versions are sequential and unique:

```text
Hydrology — version 1
Hydrology — version 2
Hydrology — version 3
```

A structural change creates a new version; it does not overwrite the previous definition.

## 3. Immutability policy

Once a schema version has been created, its structural definition is treated as immutable.

The following properties must not be modified in place:

- `schema_id`
- `schema_code`
- `name`
- `version`
- `definition`

The `description` is descriptive metadata and can be updated without creating a new structural version. This is the only field exposed by the current `DatasetSchemaUpdate` input model.

This distinction is intentional: correcting explanatory text does not change the data contract, while changing a field, data type, geometry type or CRS changes the logical structure and therefore requires a new version.

There is no requirement to introduce arbitrary `draft` or `published` states for schema records. A definition should pass validation before it is persisted.

## 4. Dataset-to-schema association

A dataset is stored in `metadata.datasets` and references the schema version it follows through:

```text
metadata.datasets.schema_id
    → metadata.dataset_schemas.schema_id
```

This association is version-specific. It does not simply point to the latest version of a schema family.

For example:

| Dataset | Schema family | Referenced version |
|---|---|---:|
| Water-level observations — north | Hydrology | 1 |
| Water-level observations — south | Hydrology | 2 |
| Rainfall observations | Meteorology | 1 |

Different datasets can therefore use different versions of the same logical schema family. Creating a new version must not automatically migrate every dataset that references an older version.

### Important distinction between identifiers

There are two different records and identifiers involved:

- `metadata.dataset_schemas.schema_id` identifies a particular logical schema version. It is immutable.
- `metadata.datasets.schema_id` is the foreign key stored on a dataset. It identifies which schema version that dataset currently follows.

When a dataset is successfully migrated to a newer version, the **dataset's foreign key** (`metadata.datasets.schema_id`) must be updated to reference the target schema version. The primary key of either schema record and its `schema_code` are never changed.

The dataset's own identity (`dataset_id`) and physical table identification (`schema_name`, `table_name`) are separate from the logical schema version. A schema migration does not, by itself, require renaming the physical table.

## 5. Creating a new version

The intended workflow for creating a subsequent version is:

1. Identify the existing schema family by its name or another stable internal reference.
2. Read the latest existing version.
3. Build and validate the new `DatasetDefinition`.
4. Assign the next version number.
5. Generate a new unique `schema_code`.
6. Insert a new row in `metadata.dataset_schemas`.
7. Preserve all previous version records.

For example, changing a schema from version 1 to version 2 creates a new record. Version 1 remains available for datasets that still use it.

The first-version creation operation (`create_schema`) assigns version 1. The service also generates the code and stores the validated definition as JSONB.

> Implementation status: the initial schema creation and description-only update have been implemented and tested. The subsequent-version workflow described above is the versioning policy; it should not be considered implemented until its service operation and tests have been added.

## 6. Dataset migration between schema versions

Creating a new schema version and migrating a dataset are two separate operations.

A new version can exist without any dataset using it. A dataset should be migrated only when its data and intended use require the new structure.

Migration is performed **per dataset**, not globally across all datasets in the schema family.

### 6.1. Intended migration workflow

A controlled migration should follow these stages:

1. **Identify the source and target**: retrieve the dataset's current schema version and the requested target version.
2. **Compare definitions**: identify added, removed or renamed fields, type changes, and geometry/CRS changes.
3. **Build a migration plan**: describe the required physical changes and data transformations.
4. **Check compatibility**: detect missing values, invalid casts, constraints, geometry incompatibilities and other risks before modifying production data.
5. **Execute safely**: use a transaction or a staging/copy strategy appropriate to the operation.
6. **Validate the result**: verify structure, record counts, required values, geometry validity and other relevant quality checks.
7. **Commit the new association**: only after successful validation, update `metadata.datasets.schema_id` to the target schema version.
8. **Record provenance**: retain the migration operation and the transformations applied.

If a migration fails, the dataset must not be left pointing to the target schema while its physical table still follows the old structure. The operation must roll back or leave the original dataset available for recovery.

### 6.2. Examples of structural changes

| Change | Potential impact | Recommended handling |
|---|---|---|
| Add an optional field | Existing rows have no value for the new field. | Add a nullable column or define a justified default/backfill. |
| Add a required field | Existing rows may not satisfy the new requirement. | Require a default or a validated backfill before enforcing `NOT NULL`. |
| Rename a field | Existing physical column name no longer matches the target definition. | Use an explicit rename/mapping; do not infer it solely from similar names. |
| Remove a field | Values may be lost if the physical column is dropped. | Do not drop automatically; assess dependencies and preserve data where required. |
| Change a data type | Conversion may fail or lose precision. | Validate conversions and rejected values before applying the change. |
| Change geometry type | Existing geometries may not satisfy the target type. | Validate and, if appropriate, transform or cast geometries explicitly. |
| Change CRS | Coordinates may need reprojection. | Apply a defined coordinate transformation and verify the output CRS. |

Adding a nullable column generally leaves existing records intact, with `NULL` in the new column. By contrast, dropping columns, narrowing types or transforming geometries can cause data loss or alter values. These operations require explicit validation and a recovery strategy.

A migration must not silently discard records or values.

## 7. Physical storage and logical schema are separate

The logical definition in `metadata.dataset_schemas.definition` describes the expected data structure. The physical records live in the dataset's PostgreSQL table.

This separation means:

- A new logical schema version does not automatically create or alter a physical table.
- A dataset can continue using its existing physical table while its migration is planned.
- The physical table name is not the schema version identifier.
- Updating a dataset's schema association is the final step of a successful migration, not a substitute for transforming the data.

The physical schema/table identifiers stored on the dataset remain independent from the logical schema's `schema_id` and `schema_code`.

## 8. History and retention

Previous schema versions provide the context needed to understand datasets and their structure over time. They should not be deleted merely because a newer version exists or because a fixed amount of time has passed.

At minimum:

- Preserve versions referenced by datasets.
- Preserve versions needed to interpret historical ingestion or transformation records.
- Do not cascade-delete historical versions as part of ordinary schema updates.
- Before any future cleanup, check references, provenance and recovery requirements.

If a schema version is no longer recommended for new datasets, a future lifecycle mechanism could mark it as retired or archived. That is different from physically deleting it and is not currently represented by a status field in the schema model.

## 9. Provenance and migration history

The metadata model already includes `ingestion_jobs` and `transformation_history`, which provide a basis for recording ingestion operations and their transformations.

A future migration workflow should reuse or extend this provenance model so that it can answer questions such as:

- Which dataset was migrated?
- Which schema version was the source?
- Which schema version was the target?
- When did the migration run, and what was its result?
- Which transformations and parameters were applied?
- How many records were inserted, updated, rejected or otherwise affected?

The exact fields and operation types needed for schema migrations must be defined when the migration service is designed. They should not be assumed to exist until added to the models and database migrations.

## 10. Current implementation versus planned behavior

| Capability | Status |
|---|---|
| Store logical schema definitions in `metadata.dataset_schemas` as JSONB | Implemented |
| Create an initial schema version (`version = 1`) | Implemented |
| Generate a unique `schema_code` in the service | Implemented |
| Retrieve schemas by ID or code and list schemas | Implemented |
| Update only the schema description | Implemented and tested |
| Prevent description updates from changing identity or definition fields | Enforced by the update input model and service logic |
| Create subsequent schema versions | Policy defined; service workflow still to be implemented |
| Compare two schema definitions and produce a migration plan | Planned |
| Execute safe physical table/data migrations | Planned |
| Update a dataset's schema reference after a successful migration | Planned |
| Record source/target schema versions in migration provenance | Planned |

This separation is important: this document describes both the current design and the intended evolution, but it does not claim that the future migration engine is already available.
